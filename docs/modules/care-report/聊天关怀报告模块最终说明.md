# 聊天关怀报告模块：最终实验与交付说明

## 1. 这个模块到底是什么

它不是诊断工具，也不是替家人“读心”。

它处理的是老人平时和 AI 的自然语音聊天：当老人说到想有人联系、想一起参加活动、看不清表格、办事困难或出行安全顾虑时，系统把这些话整理成一条简短的家人关怀提示和一项可执行建议。家人看不到聊天原话，只能看到经过安全校验后的概括。

它要解决的是：老人常常不愿直接麻烦家人；家人没有时间从日常聊天里猜老人到底需要什么。AI 的职责只是提醒“这周可以先关心什么”，真正联系、陪伴或协助仍由家人完成。

## 2. 已经落地的功能链路

```text
老人语音聊天
  → 语音模块转文字（本模块不修改语音功能）
  → 只取老人自己说过的内容，最多 40 轮
  → deepseek-v4-flash 生成受限 JSON
  → 程序安全校验与降级
  → 已绑定家人主动点击生成
  → 家人只看到概括、关怀类别和行动建议
```

### 两类关怀与四类动作

| 关怀类别 | 适用情形 | 允许的家人动作 |
|---|---|---|
| `psychological` | 陪伴、联系、孤单、情绪支持、参与活动 | `contact_companionship`（主动联系/倾听）；`shared_activity`（一起参与活动） |
| `physical_or_daily` | 看不清、日常办事、搬重物、影响出行安全的描述 | `daily_step_support`（具体日常协助）；`safety_check`（先确认安全/陪同处理） |

这不是给“疾病”分类。出现身体不适描述时，系统只能提醒家人关注安全，不能给出疾病、治疗、处方或用药建议。

### 安全边界已经写进代码

程序会拒绝或降级以下输出：疾病/诊断/治疗/医院/用药等医疗化表述、超过 10 个连续字符的聊天原话、无效来源轮次、类别和动作不匹配、缺少动作类别的信号。普通闲聊、已解决问题、明确拒绝帮助或线索矛盾时，系统输出“暂不形成关怀提示”。

家人页面只读取 `area`、`topic`、`strength`、`trend` 和 `family_action`；不会显示聊天原话、`source_turn_ids` 或内部 `action_type`。

## 3. 为什么不能只跑一个数据集

本项目的目标不是普通情感分类，而是“从老人和 AI 的聊天里，保守地生成给家人的关怀提示”。公开数据中没有一个数据集同时具备：老人身份、自然聊天、潜在家庭需求、家人行动标签、真实长期结果。因此把不匹配的数据硬算成“准确率”反而不严谨。

所以最终测试分成三层，每层只回答自己能回答的问题。

| 层级 | 数据与规模 | 测什么 | 能说明什么 | 不能说明什么 |
|---|---:|---|---|---|
| 主验证 | 48 个中文冻结任务案例 × 3 次 = 144 次 | 类别、动作、克制、改写/干扰/反转、稳定性 | 系统是否符合本项目定义的行为 | 真实老人群体准确率、医疗有效性 |
| 老年领域覆盖 | CareCall 60 段老年用户—系统对话 × 1 次 | 老年对话输入下的结构、耗时、保守分布 | 在更接近老人聊天形式的公开语料上能否稳定运行 | 家庭关怀需求准确率；CareCall 没有该真值 |
| 心理迁移检查 | ESConv 32 段未缓解情感支持对话 × 2 次 = 64 次 | 多类情感支持场景的心理线索敏感性 | 在不同负性支持情境中能否识别心理关怀线索 | 老人场景、家人行动或潜在需求真值 |

最终代码对应的真实模型调用合计为 **268 次**。所有结果文件只保留案例/语料编号、标签、耗时和错误类型；审计确认不含对话正文或模型原文。

## 4. 主验证：48 个冻结中文案例

案例在调用模型前已经写定，涵盖：

- 8 个明确心理陪伴/活动线索；
- 8 个明确日常协助/安全线索；
- 16 个应该克制的案例（普通闲聊、已经解决、明确拒绝、信息不足）；
- 16 个成对鲁棒性案例（同义改写、加入无关聊天、后续解决或拒绝）。

| 指标 | 最终结果 | 解释 |
|---|---:|---|
| 合格结构化报告 | 140 / 144（97.2%） | 4 次被安全闸门拒绝，不会展示给家人 |
| 类别 Precision | 95.5% | 输出的类别很少多报 |
| 类别 Recall | 88.9% | 严格安全规则下有保守漏报 |
| 类别 F1 | 92.1% | 主验证的核心结果，应作为 PPT 使用数字 |
| 无信号时正确克制 | 72 / 72（100%） | 闲聊、已解决、明确拒绝时没有强推提示 |
| 明确线索完全匹配 | 63 / 72（87.5%） | 类别和动作都同时符合预期 |
| 行动类别完全匹配 | 135 / 144（93.8%） | 大多数建议落在预期动作类型 |
| 改写/干扰/反转鲁棒性 | 45 / 48（93.8%） | 改说法、加闲聊、后续解决后大多保持正确行为 |
| 三次完全稳定 | 45 / 48（93.8%） | 同一案例三次的结构结果通常一致 |
| 安全闸门 | 10 / 10（100%） | 医疗化措辞、原话、无效来源、错配动作等均被拦截 |
| API 错误 | 0 | 无接口失败 |
| 平均耗时 | 3.12 秒 | 一次家人主动生成报告的平均时长 |

### 未匹配结果没有被删除

主验证中共有 8 个应有类别没有输出、3 个额外类别。主要原因有两类：

1. 模型把“外出看展、路线不熟、一个人没底”理解成日常协助，而预设答案把它归为陪伴活动；这是“陪伴”和“日常协助”的真实语义边界。
2. 个别包含药盒/挂号等词的输入，会使模型输出医疗化措辞，随后被安全闸门拒绝。系统选择不向家人展示该报告，而不是输出未经约束的医疗建议。

这也是为什么最终 F1 是 92.1%，而不是引用修复前较高的小集成绩。对本项目而言，安全地不报比医疗化地乱报更合适。

## 5. CareCall：老年对话领域覆盖

CareCall for Seniors 是专门面向老年关怀场景的角色指定开放域对话语料。使用其中 200 段人工翻译样本中的 60 段：`validated` 与 `fixed` 子集各 30 段。原语料由 LLM 生成并有人类筛选/修订，角色字段明确区分老年用户与系统。

| 结果 | 数值 |
|---|---:|
| 运行数量 | 60 段 × 1 次 = 60 次 |
| 合格结构 | 58 / 60（96.7%） |
| 形成关怀提示 | 12 |
| 暂不形成提示 | 46 |
| 安全拒绝 | 2 |
| 心理类别出现 | 7 |
| 日常/安全类别出现 | 9 |
| 平均耗时 | 5.01 秒 |
| API 错误 | 0 |

这个结果支持“面对老年人—AI 对话形式，模块能够稳定、保守地运行”。它**不**支持“在老人真实需求上有 96.7% 准确率”，因为 CareCall 没有家庭关怀需求真值，并且不是本项目的中文真实用户数据。

## 6. ESConv：心理关怀迁移检查

ESConv 是公开的情感支持对话数据集。为避免随机取样，本次固定了四种带负性情绪、且对话结束时寻求者情绪强度仍不低于 3 的问题类型：持续低落、工作危机、分手、朋友关系问题；每类 8 段，每段运行 2 次。

| 结果 | 数值 |
|---|---:|
| 运行数量 | 32 段 × 2 次 = 64 次 |
| 合格结构 | 64 / 64（100%） |
| 心理关怀线索敏感性 | 84.4% |
| 持续低落 | 87.5% |
| 工作危机 | 68.8% |
| 分手 | 93.8% |
| 朋友关系 | 87.5% |
| 平均耗时 | 11.59 秒 |
| API 错误 | 0 |

ESConv 的标签是“情感支持问题/情绪”，不是“老人是否需要家人做什么”。因此 84.4% 只能说明模型在多种尚未缓解的情感支持场景中，较常识别到心理关怀线索；不能当作本项目的 F1 或老人需求准确率。

## 8. 可以怎样向老师说明

“我们没有声称 AI 能通过聊天诊断老人，也没有说它能知道老人所有真实需求。我们做的是一个受限的家庭沟通提示器：只使用老人和 AI 的聊天，只向已绑定家人展示概括和一条行动建议；信息不足、问题已解决、老人拒绝帮助或输出触及医疗化边界时，系统会选择不提示。我们用 48 个任务对齐冻结案例验证正确性和克制性，用老年对话语料验证领域可运行性，用情感支持语料验证心理线索迁移。三类证据分开报告，误差和安全拒绝也保留在结果中。”
