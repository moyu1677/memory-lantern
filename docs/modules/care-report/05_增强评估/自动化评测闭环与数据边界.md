# 聊天关怀报告：自动化评测闭环与数据边界

**这是当前执行方案。** 它替代“以人工体验为主”的早期设想。

## 1. 先把两个事实说清楚

### 事实一：没有答案，就不能叫准确率

“从老人聊天中提取潜在需求”没有天然正确答案。除非老人本人或其家人事后确认“他当时确实希望家人做这件事”，否则任何人都不能从一段对话反推出唯一真实需求。

所以：

- 不能把一段真实老人聊天交给模型，再把模型结果当作“真实答案”；
- 不能用聊天内容里出现的疾病词来充当需求标签；
- 不能把模型评委的分数说成真实需求准确率。

真正有正确答案的，只有**在测试开始前已经写明预期结果的案例**。这类案例是“受控基准”，不是“真实老人临床数据”。

### 事实二：公开数据不能替代这份真值

我核对了三类最接近的公开资源：

| 资源 | 它有什么 | 为什么不能直接当本项目的真实答案 |
|---|---|---|
| [SeniorTalk](https://mlanthology.org/neurips/2025/chen2025neurips-seniortalk/) | 202 位 75–85 岁人群、101 段自然中文对话，面向语音任务 | 标签服务于说话人、分离、识别、编辑等语音任务，没有“需要家人做什么”的标注 |
| [ESConv](https://github.com/thu-coai/Emotional-Support-Conversation) | 1,300 段人工情感支持对话，含问题类别、情绪、支持策略与反馈 | 不是老人场景，且它标的是求助者的问题和支持者策略，不是“家庭关怀需求” |
| [COCOON](https://aclanthology.org/2025.emnlp-main.1094/) | 中文隐性情感需求与主动支持方向 | 研究方向很接近，但不是老人家庭场景；其重点是支持对话策略，不可直接拿来宣称家庭需求真值 |

因此，本项目不应强行寻找一个不存在的“真实老人需求标准数据集”。公开数据只能证明问题方向和语言场景值得研究，不能为我们的完整功能背书。

## 2. 当前采用的真值来源：受控参考基准

我们采用 **24 个预先冻结的受控案例**。每个案例都在模型运行前写好答案，由团队根据项目定义制定；运行后不允许改答案。

```json
{
  "id": "daily_form_help",
  "expected_status": "signals_present",
  "expected_areas": ["physical_or_daily"],
  "expected_action_type": "日常分步协助",
  "expected_source_turn_ids": [2, 3],
  "history": ["..." ]
}
```

这里的“答案”不是在猜老人内心，而是回答一个更严谨的问题：

> 在这个明确设计的对话条件下，系统是否把已经写明的关怀线索、状态和建议类型识别出来？

### 案例数量与覆盖范围

不需要做上百个案例。24 个足够形成完整逻辑：

| 组别 | 数量 | 正确答案是什么 | 要证明什么 |
|---|---:|---|---|
| 明确心理/陪伴线索 | 4 | 应提示 `psychological` + 对应行动 | 能识别陪伴与联系需要 |
| 明确生活/身体线索 | 4 | 应提示 `physical_or_daily` + 对应行动 | 能识别日常协助与安全留意 |
| 无需推送 | 2 | `insufficient_or_conflicting` | 不把普通聊天当问题 |
| 已解决 | 2 | `insufficient_or_conflicting` | 新信息能覆盖旧问题 |
| 明确拒绝帮助 | 2 | `insufficient_or_conflicting` | 尊重老人明确意愿 |
| 信息前后矛盾 | 2 | `insufficient_or_conflicting` | 不强行下结论 |
| 同义改写对 | 4 | 与原案例相同类别和行动 | 不因换一种说法而误判 |
| 闲聊干扰 / 状态反转对 | 4 | 保持或按新状态撤回 | 长聊天与时间变化下仍可靠 |

现有的开发集与最终 holdout 可复用为其中一部分；新增案例只补上“建议类型”和成对鲁棒性字段，不需要重新训练模型。

## 3. 只保留五组指标，每组都回答不同问题

| 指标 | 正确答案来自哪里 | 它回答的问题 | 为什么必须有 |
|---|---|---|---|
| **类别 Precision / Recall / F1** | `expected_areas` | 该提示时有没有识别到？不该出现的类别有没有乱报？ | 同时暴露漏报和多报，不能只报命中率 |
| **克制正确率** | 无需推送、已解决、拒绝、矛盾案例的 `expected_status` | 系统会不会把普通或已结束的事推给家人？ | 这是家庭关怀场景最重要的安全能力 |
| **行动匹配率** | `expected_action_type` | 建议是否对应实际需要，而不是泛泛地说“多联系” | 证明报告具有可行动性和个性化 |
| **成对鲁棒率** | 改写/干扰/状态反转对的预设关系 | 换一种说法、加入闲聊、后来解决后，结果是否合理变化？ | 证明它不是只碰巧命中关键词 |
| **保护规则通过率** | 固定的攻击与越界案例 | 是否泄露原话、给诊断、输出无效来源、越权展示？ | 证明系统不会因“提取能力”牺牲安全 |

结构化成功率、平均耗时和三次运行稳定性继续保留为工程指标，但不放在 PPT 主表中。

### 指标如何计算

```text
Precision = 正确输出的类别 / 全部输出的类别
Recall    = 正确输出的类别 / 全部应输出的类别
F1        = Precision 与 Recall 的平衡值

克制正确率 = 正确输出“暂不形成提示”的次数 / 全部无需推送案例次数
行动匹配率 = 建议类型正确的次数 / 全部案例次数
成对鲁棒率 = 满足预设成对关系的次数 / 全部成对测试次数
保护规则通过率 = 未越过任何保护规则的次数 / 全部攻击案例次数
```

每一项都由 JSON 中已经冻结的字段自动计算，不需要人工逐条评分，也不需要让模型为自己打分。

## 4. 人工只保留为小型审计，不作为主结果

如果有人可以花很少时间看样本，只做一件事：随机抽 6 份报告，由两位项目成员各自勾选：

1. 是否比聊天内容多说了事实；
2. 是否把已解决/拒绝帮助的情况误推送；
3. 建议是否明显不合适或越界。

这不是“用户体验研究”，也不能统计出人群结论。它只用于检查自动测试没有覆盖到的明显错误。若来不及做，不影响主评测闭环。

---

## 5. 证据支持率如何处理

此前提出的 NLI“证据支持率”可以保留为**附加检查**，不能作为核心准确率：它验证“模型输出是否被指定对话轮次支持”，但 NLI 仍是另一个模型，并不产生真实需求答案。

这个思路可参考 [FActScore](https://aclanthology.org/2023.emnlp-main.741/) 的原子事实核验，以及 [SummaC](https://aclanthology.org/2022.tacl-1.10/) 的细粒度对齐；但在本项目中，它只用于拦截可疑报告，主结果仍以冻结真值案例为准。

---

## 6. 最终可对老师说的话

> 我们没有把真实老人聊天擅自标成“真实需求答案”。由于公开数据并不存在“老人自然聊天、家庭需求和事后确认”三者同时具备的标准集，我们建立了运行前冻结、包含正例、拒绝、已解决、矛盾和改写干扰的受控参考基准。所有主指标都由预设答案自动计算，分别验证识别、克制、行动建议和鲁棒性；真实老人语料只作为语音与场景研究参考，不被夸大为需求准确率证据。

这比找几段真实聊天、再让模型给自己打分更严谨，也更诚实。
