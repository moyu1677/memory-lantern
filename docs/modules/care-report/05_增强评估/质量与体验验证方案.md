# 聊天关怀报告：质量与体验验证升级方案

## 先说结论

现在的 27 次冻结案例结果，证明的是：**报告能稳定生成、能保护隐私、在没有足够依据时多数情况下会克制。**

它还不能充分证明两件更重要的事：

1. 每一条提示是否真的能被老人聊天内容支持；
2. 这份提示是否真的能让家人更快、更合适地做出行动。

因此不要继续堆“模型命中率”，而是补成三个层次：

```text
聊天内容是否支持报告？     → 依据层
模型是否识别正确、懂得克制？ → 提取层
家人是否更快知道该做什么？  → 体验层
```

这不是医疗验证，也不把它包装为临床诊断；它要证明的是：**作为家人关怀提醒，这个功能是有依据、不过度、且有实际帮助的。**

---

## 1. 现有指标为什么不够

当前已有：结构化成功率、明确需求命中、无信号时克制、类别一致性、三次稳定性、耗时与权限检查。

这些指标更像“工程验收”。它们缺少：

- 报告中每一条具体说法是否有聊天证据；
- 模型是否漏掉真正重要的线索，或额外加入不该有的类别；
- “已经解决”“明确拒绝帮助”“被大量闲聊包围”的情况是否仍然稳健；
- 家人看完后，是否更快选对合适的下一步；
- 家人是否觉得它有用、清楚、但没有越界。

现有最终 holdout 结果可以补算出一个更完整的提取起点：按“案例—类别”计，正确类别 10 个、漏掉 2 个、额外多报 1 个类别，因此：

| 指标 | 当前可从 27 次结果补算的值 | 含义 |
|---|---:|---|
| 类别精确率（Precision） | 10 / (10 + 1) = **90.9%** | 推送出来的类别大多正确，但有一次多报 |
| 类别召回率（Recall） | 10 / (10 + 2) = **83.3%** | 轻度、含蓄需求仍可能漏掉 |
| 类别 F1 | **87.0%** | 精确率与召回率的平衡值 |
| 无信号特异性 | 15 / 15 = **100%** | 不应提示时没有强推报告 |
| 三次完全稳定率 | 7 / 9 = **77.8%** | 两个边界案例仍有波动 |

这些数值不能被表述为真实老人群体准确率；它们只是在冻结合成案例上的系统行为结果。

## 2. 新的核心方法：证据优先，而不是让模型“凭感觉总结”

### 2.1 轻量改造思路

不做“每句话都嵌入隐空间”，也不长期存储全部聊天，更不训练新模型。

当前系统已经要求模型返回内部 `source_turn_ids`。下一步只需把每条候选提示先整理成一个**内部证据卡**，再生成家人可读的四行报告：

```text
候选提示
├─ 关怀类别：陪伴 / 生活与身体
├─ 当前状态：仍需关注 / 已解决 / 明确拒绝 / 信息冲突
├─ 支持来源：本次对话的轮次编号（只供程序核验）
├─ 建议类型：联系、陪伴、分步协助、安全留意
└─ 家人页面：只显示概括和建议，不显示上述内部证据或原话
```

报告只有在“仍需关注 + 有可核验来源”时才展示；后续一句明确的“已经解决”或“不用麻烦”会使旧卡失效。

这比单纯让大模型写摘要更可解释，也能直接测量“报告有没有依据”。

### 2.2 论文依据

- [FActScore（Min et al., EMNLP 2023）](https://aclanthology.org/2023.emnlp-main.741/) 的关键不是它的具体工具，而是“把输出拆成原子事实，逐条检查是否被来源支持”的思路。这里可把“类别、状态、趋势”作为原子主张逐条验。
- [SummaC（Laban et al., TACL 2022）](https://aclanthology.org/2022.tacl-1.10/) 强调按句对齐、再聚合比整篇文本直接比较更可靠。这里可让每条内部证据卡只对齐它标记的老人轮次，而不是让一个分数判断整段长聊天。
- [G-Eval（Liu et al., EMNLP 2023）](https://aclanthology.org/2023.emnlp-main.153/) 可作为辅助的“按固定量表评文字”方法；但该论文也指出模型评委可能对模型文本有偏好。因此本项目不能把 LLM 打分当主证据，只能作为补充。

## 3. 建议采用的五组指标

### A. 提取是否正确：类别精确率、召回率与 F1

**测什么：** 是否正确识别了“心理与陪伴”或“生活与身体”，是否漏掉或多报。

**怎么测：** 在冻结案例中，为每个案例预先写好 `expected_areas`；按“案例—类别”计算：

```text
Precision = 正确输出的类别 / 全部输出的类别
Recall    = 正确输出的类别 / 全部应输出的类别
F1        = Precision 与 Recall 的平衡值
```

这比只报“命中率”更完整，因为它同时暴露“漏报”和“乱报”。

### B. 报告是否有依据：证据支持率（Evidence Support Rate）

**测什么：** 报告里的“类别、状态、趋势”有多少真正能被对应聊天支持。

**怎么测：**

1. 把每份报告拆为最多三条原子主张，例如“存在日常协助线索”“该问题仍未解决”；
2. 只拿该卡记录的来源轮次，与这条主张做蕴含/矛盾/未知判断；
3. `证据支持率 = 被支持的原子主张数 / 全部原子主张数`。

建议使用与生成模型不同的、开源多语言 NLI 校验器作为第一道自动核验，例如 [mDeBERTa-v3-base-mnli-xnli 的模型卡](https://huggingface.co/MoritzLaurer/mDeBERTa-v3-base-mnli-xnli)说明其支持多语言 NLI；它可在服务器本地运行。它不作医疗判断，只回答“这句话能否从这几轮聊天推出”。

NLI 本身也会出错，所以该指标应报告为“自动证据核验结果”，而不是绝对事实。对验证集中 NLI 判断为“未知/矛盾”的报告，系统应优先不推送或降为“之后再留意”。

### C. 是否懂得克制：拒绝、解决与干扰鲁棒性

当前 15 / 15 的“无信号时不提示”是一个好的开始，但要补成三类成对测试：

| 成对案例 | 要观察什么 | 指标 |
|---|---|---|
| 有需求 → 最新一句说明已解决 | 是否撤回旧提示 | 解决修正率 |
| 有需求 → 最新一句明确拒绝帮助 | 是否不再推送 | 拒绝尊重率 |
| 同一需求 → 前后插入大量天气、兴趣闲聊 | 是否仍保留同一类别与建议 | 干扰不变率 |
| 原话替换为同义说法 | 是否保留相同核心判断 | 改写一致率 |

这四项比“多跑三次模型”更贴近真实长聊天，也能直接回应“不能因为一句相似的话就误判”的担忧。

### D. 建议是否真的对应需求：行动匹配率

**测什么：** 家人建议有没有落在正确的帮助方式上，而不是只会说“多关心一下”。

冻结案例需要额外写一个小字段：

```json
"expected_action_type": "陪伴联系 / 共同参与 / 日常分步协助 / 安全留意 / 暂不行动"
```

程序把模型建议归入这五类后，计算：

```text
行动匹配率 = 建议类型正确的案例数 / 全部案例数
```

这一项恰好测到系统的“个性化价值”：不是只知道老人不舒服，而是能把不同线索转成不同的家人动作。

### E. 家人是否真的更快理解：情境任务体验验证

这部分不能只让模型自己打分，但也不需要大规模人工标注或问卷。

做一个很小的、可演示的“家人角色体验”：每位参与者只看 3 个预先写好的情境，每个情境都有明确答案（老人是否需要联系、先做什么）。系统随机给参与者看两种材料之一：

1. **对照组：** 普通聊天概括或零散聊天信息；
2. **本项目组：** 当前家庭关怀报告。

让参与者在阅读后完成三个选择：

- 老人当前最可能需要哪一类帮助？
- 此刻是“主动联系 / 之后留意 / 暂不行动”哪一种？
- 第一个最合适的行动是什么？

记录而非主观猜测：

| 指标 | 如何记录 | 为什么有用 |
|---|---|---|
| 理解正确率 | 与预设情境答案比对 | 看家人是否理解老人需要什么 |
| 安全决策正确率 | 是否避免漏联系与过度联系 | 看报告是否会误导家人 |
| 完成时间 | 从看到材料到提交选择的秒数 | 看报告是否节省家人时间 |
| 行动选择正确率 | 与 `expected_action_type` 比对 | 看建议是否可执行 |

这样不需要人工去标“每一段真实聊天的正确答案”，因为答案在冻结情境建立时已经写好。参与者真正体验的是“看完报告后我能不能马上知道怎么做”。

体验结束后只追加两道简短主观题：

1. “这份报告能帮助我更快决定是否该主动关心老人。”
2. “这份报告的表达清楚、不过度，也没有让我觉得被隐私冒犯。”

用 1–7 分展示每个人的分布和中位数，不把少量体验者包装成大样本统计结论。若想要一个有成熟来源的超短可用性量表，可以使用 [UMUX-Lite（Lewis et al., CHI 2013）](https://doi.org/10.1145/2470654.2481287) 的两题框架；它本来就是为时间有限的场景设计。技术接受模型 TAM 也把“感到有用”和“感到易用”作为接受技术的两个基本维度，[Davis 1989](https://doi.org/10.2307/249008)。中文改写题只能称为“试点评价”，不能假装是经过中文版信效度验证的量表。

## 4. 最小落地包：不把任务做大

本项目不需要训练新模型，也不需要收集长期真实老人聊天。真正需要新增的只有四项：

1. 在现有 9 个 holdout 案例旁补充 `expected_action_type`；再新增 8 个成对鲁棒性案例（已解决、拒绝、干扰、改写各 2 个）。
2. 新建一个评测脚本，统一输出：类别 Precision / Recall / F1、特异性、解决修正率、拒绝尊重率、干扰不变率、行动匹配率与三次稳定率。
3. 给当前 `source_turn_ids` 加上内部“状态 + 建议类型”字段，并用独立 NLI 做证据支持率核验；只在服务端保留，不展示原话。
4. 做一次小型家人角色体验，展示“理解正确率、行动正确率、完成时间”，并把参与人数、场景数和局限性如实写出来。

如果来不及做第 3 项，前两项加第 4 项也已经明显强于目前的单一模型命中率；第 3 项是让技术说服力更强的优先增强项。

## 5. PPT 应该怎样说

不要说：“我们的 AI 准确率很高，所以能判断老人需求。”

应该说：

> 我们把系统评价分为三步：先确认提示能被聊天证据支持，再确认模型在无信息或问题已解决时会保持克制，最后通过带标准答案的家人情境任务，观察报告是否让家人更快选对合适行动。它不替代诊断，而是让家人少猜一点、行动更合适一点。

这句话比单报一个 83.3% 或 88.9% 更完整，也更诚实。
