# 忆路明灯：家庭关怀报告与双报告融合说明

**用途：** 作为项目当前定案、PPT 内容准备和老师验收说明。
**项目目标：** 不是替老人诊断疾病，也不是让 AI “读心”；而是在老人和 AI 的自然语音聊天中整理少量值得家人主动关心的线索，再结合认知测评结果，帮助家人在很短时间内知道“该先关心什么、可以怎么开口”。

---

## 1. 项目最终要做的东西

系统最终面对两个角色：

- **老人：** 平时可用语音和 AI 聊天。AI 使用家人授权的声音回复，减少陌生机器感；老人不需要填写长问卷，也不需要逐条确认“我是不是有需求”。
- **家人：** 看到一份简短、克制、可行动的家庭关怀报告。报告只是提示家人发起真实联系，不替家人作决定。

项目有两份来源不同的报告：

| 报告 | 回答的问题 | 不能回答的问题 |
|---|---|---|
| 日常聊天关怀报告 | 最近是否出现陪伴、生活或身体日常支持的线索？ | 是否患病、是否一定存在某种心理问题 |
| MoCA / 认知测评报告 | 本次标准化认知筛查中，哪些维度需要施测者进一步关注？ | 老人真正想要家人做什么、疾病诊断 |

两份报告不是互相替代，而是互补：**聊天更接近日常需要，认知测评更接近结构化的认知支持提示。**

---

## 2. 已完成的聊天提取模块

当前已接入 `deepseek-v4-flash`。模型只从老人—AI 对话中输出两类有限信号：

1. `psychological`：陪伴、联系、孤独感、情绪支持、参与活动；
2. `physical_or_daily`：行动、睡眠、视听、日常自理、家务安全、身体不适等实际困难。

在结果进入家人页面前，系统会做规则校验：

- 不接受疾病诊断、处方或用药调整；
- 不显示完整聊天，不显示来源轮次；
- 拒绝复制老人输入中连续 10 个及以上字符，避免原话泄露；
- 只接受当前会话中真实存在的来源轮次；
- 对普通闲聊、已解决问题、明确拒绝帮助或前后矛盾的信息，输出“暂不形成关怀提示”。

家人端最终只看到概括性提示和一项温和建议。

---

## 3. 已完成的真实验证结果

测试使用 9 个预先冻结的合成多轮对话，每个案例真实调用 `deepseek-v4-flash` 3 次，共 27 次。结果不保存测试聊天原文或模型原文，只保存类别、通过情况和耗时。

| 指标 | 结果 | 说明 |
|---|---:|---|
| 合格结构化报告 | 27 / 27（100%） | 所有调用都返回了可校验、可展示的 JSON 报告 |
| 明确关怀需求命中 | 10 / 12（83.3%） | 大多数明确需求可被识别；轻度、含蓄协助需求仍可能漏报 |
| 无信号时正确克制 | 15 / 15（100%） | 普通闲聊、已解决问题、明确拒绝帮助均未被强行推送 |
| 状态与类别完全一致 | 24 / 27（88.9%） | 采用最严格的“状态和类别都一致”计算 |
| 三次运行完全稳定 | 7 / 9（77.8%） | 2 个边界案例存在类别或是否提示的波动 |
| 平均模型生成耗时 | 3.40 秒 | 不含网页操作 |
| API 错误 | 0 | 27 次真实调用均完成 |

端到端验收也已完成：老人连续聊天、家人生成报告、家庭页不泄露原话、管理员验证页和未绑定家人的权限拦截均实际跑通；完整自动化回归为 **51 passed**。

### 这组数据能证明什么

可以证明：当前“聊天 → 结构化关怀信号 → 家人报告”的工程链路真实可运行，而且对“没有足够依据时不打扰家人”比较保守。

不能证明：AI 能识别所有真实老人需求、能诊断疾病、或对真实老年群体具有临床准确率。项目应始终把它表述为**关怀提醒工具**。

完整实验记录见 `CHAT_REPORT_VALIDATION.md`；管理员可在网页“关怀验证”页查看不含原话的汇总指标。

## 4. 下一阶段：把两份报告变成一页家庭简报

### 核心原则

**不新训练模型，不让大模型给认知分数下结论。**

最稳妥的结构是：

```text
聊天关怀报告 ─────┐
                  ├─→ 固定融合规则 ─→ 一页家庭行动简报
MoCA 认知报告 ────┘                 （必要时只让模型润色语言）
```

- MoCA 保留原有标准化分数、维度与施测提示；融合层不能重算分数，也不能把它写成“确诊”。
- 聊天报告保留心理/陪伴与生活/身体日常支持信号。
- 融合层只决定：本周是否值得关心、来自哪个来源、家人可以做的一件事。
- DeepSeek 如参与最终文字生成，只能根据已经确定的结构化字段改写成易懂中文，不能新增类别、严重程度或医疗结论。

### 融合规则

| 输入情况 | 家庭简报应怎么说 | 不应怎么说 |
|---|---|---|
| 聊天和认知报告都指向同一类日常困难 | “近期可协助把这件事拆成步骤完成，并观察是否仍有困难。” | “这证明认知已经退化。” |
| 只有聊天有线索 | “最近可主动问问是否需要陪伴或实际帮助。” | “因为孤独，所以患有抑郁。” |
| 只有 MoCA 需关注 | “下次涉及复杂事项时，可主动提供分步提醒；如困扰持续，再考虑正式咨询。” | “测评已经说明他无法独立生活。” |
| 两份信息矛盾或不足 | “目前不作结论，之后自然聊天或下次测评时再留意。” | 强行把两份信息解释为同一件事 |
| 未授权或家人未绑定 | 不生成、不展示 | 以任何形式分享老人内容 |

### 家人实际看到的格式

```text
本周值得留意：安排复杂事务时，老人可能更希望得到分步协助。
信息来源：聊天 + 认知测评。
家人可以做：下次预约、缴费或出行前，先问是否愿意一起把步骤写下来。
说明：这是一项关怀提示，不是医疗诊断。
```

家人只需要读完这四行，不需要猜老人到底想表达什么。

## 5. 可引用的论文与框架

| 文献 / 框架 | 在本项目中的作用 | 不能被用来证明什么 |
|---|---|---|
| [Nasreddine et al., 2005：MoCA 原始验证研究](https://pubmed.ncbi.nlm.nih.gov/15817019/) | 说明 MoCA 是认知筛查工具，应保持标准化边界 | MoCA 本身不是疾病诊断，也不能推断家庭陪伴需求 |
| [WHO ICOPE 指南](https://www.who.int/publications/i/item/9789240103726) | 提供“认知、心理、行动、感官、日常能力”并列关注的老年人整体框架 | 不能把 ICOPE 当成本项目的诊断算法 |
| [Fu et al., 2025：COCOON](https://aclanthology.org/2025.emnlp-main.1094/) | 支持“从含蓄表达中识别潜在情感需求”这一方法方向 | 数据不等于真实老人日常聊天，也不覆盖医疗判断 |
| [Ribeiro et al., 2020：CheckList](https://aclanthology.org/2020.acl-main.442/) | 支持用冻结案例、否定案例、改写案例验证 NLP 系统是否稳定和克制 | 不能单独证明真实临床效果 |

当前没有一个公开模型可以直接把“中文老人聊天 + MoCA 结果”可靠地融合成真实需求或诊断。因此，本项目的创新应放在**受约束的融合规则和家庭可行动简报**上，而不是包装成医疗大模型。

## 6. 融合阶段最少需要的评测

不需要重新收集大量数据，也不需要训练模型。做 **12 个冻结融合案例** 就够：

- 3 个“两份报告指向同一件实际困难”；
- 3 个“只有聊天有线索”；
- 2 个“只有 MoCA 需关注”；
- 2 个“信息矛盾或已解决”；
- 1 个“无明显线索”；
- 1 个“未绑定/未授权”。

| 指标 | 要检查的问题 | 为什么重要 |
|---|---|---|
| 融合规则正确率 | 是否正确选中“聊天 / MoCA / 两者 / 暂不判断” | 防止两份信息被乱拼 |
| 错误关联率 | 是否把无关聊天线索和 MoCA 结果说成因果 | 这是最危险的误导类型 |
| 安全克制率 | 矛盾、缺失、未授权时是否不给结论 | 比“多报几个提示”更重要 |
| 行动建议合格率 | 是否只给一项具体建议，且无诊断、处方、原话 | 确保家人能真正使用 |
| 稳定性 | 同一案例运行 3 次，来源和建议是否一致 | 若最终仍用 LLM 润色，这项必须保留 |

不建议把 BLEU、ROUGE 当核心指标，因为文字相似不等于建议正确、安全或有用。

## 7. PPT 可直接使用的主线

1. **问题：** 年轻人没有时间长期陪伴；老人又不愿直接开口。
2. **方法：** 语音陪伴聊天提取关怀线索；MoCA 提供认知支持提示；两者不诊断，只生成家人行动建议。
3. **可信性：** 展示 27 次真实 API 测试表格，特别强调 15/15 的“无信号时正确克制”。
4. **结果：** 家人只需阅读一页简报，即可知道“该关心什么、来自哪里、下一步怎么做”。
5. **边界：** 不替代医生、不读心、不展示原话；信息矛盾时明确暂不判断。

这条主线比“我们接了很多 AI 功能”更清楚：**系统的价值是降低代际沟通门槛，同时用规则让 AI 保持克制。**
