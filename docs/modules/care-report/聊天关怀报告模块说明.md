# 聊天关怀报告模块说明

## 1. 这个模块到底做什么

它不是“监控老人聊天”，也不是根据几句话诊断老人是否生病。

它做的是一件很具体的事：**老人平时和 AI 自然聊天后，系统从老人主动说出的内容中整理少量可能值得家人关心的线索，并把线索改写成家人能快速看懂的一条提示和一项行动建议。**

例如，老人反复提到一个人参加活动不方便、但又不愿主动麻烦子女，家人看到的不是聊天原话，而是：

```text
本周值得留意：老人近期可能更希望在外出活动上得到陪伴。
家人可以做：这周主动问问是否愿意一起去一次附近活动。
说明：这是关怀提示，不是医疗诊断。
```

它要打破的是“老人不愿开口，家人没时间猜”的交流壁垒。真正联系老人、提供陪伴或帮助的人仍然是家人，AI 只负责给出克制的提醒。

---

## 2. 它解决什么问题，不能解决什么问题

| 可以帮助的事 | 不能做的事 |
|---|---|
| 把含蓄出现的陪伴、生活协助或安全留意线索整理给家人 | 读取老人和家人的私聊 |
| 提醒家人主动问一句、帮一步、陪一次 | 断言老人“真实内心一定是这样” |
| 在问题已解决、老人拒绝帮助或信息矛盾时选择不推送 | 诊断抑郁、认知障碍、疾病或开药 |
| 让家人在较短时间内知道“先关心什么” | 代替家人、医生或正式社会服务解决问题 |

所以它可以帮助老人**更容易被家人看见和回应**，但不能保证一个提示一定解决需求，更不能把“提示”说成“结论”。

## 3. 模块在整个项目中的位置

```text
老人语音说话
    ↓  （语音识别模块转成文字）
老人—AI 自然聊天
    ↓
【聊天关怀报告模块】
只读取老人说过的话 → 提取关怀线索 → 安全校验
    ↓
家人已绑定账户主动生成报告
    ↓
概括性提示 + 一项家人行动建议
```

### 与其他模块的关系

| 相连模块 | 本模块如何使用它 | 不做什么 |
|---|---|---|
| 语音识别、语音合成、家人授权声音 | 为老人提供自然的语音聊天入口和熟悉的回复声音 | 本模块不训练、修改或评估语音模型 |
| 账户与家人绑定 | 只有已绑定家人能看到对应老人的报告 | 不让未绑定人员生成或读取报告 |
| 数据库 | 保存已校验的概括、类别、建议与时间 | 不把聊天原话写入关怀报告 |
| 家人报告页面 | 展示短报告与建议 | 不展示原话、内部来源轮次或模型推理 |
| 管理员验证页面 | 展示冻结案例上的汇总数据 | 不展示测试对话或个人信息 |
| MoCA 认知测评模块 | 当前没有直接调用关系；未来可在独立融合层并列展示两份报告 | 本模块不计算 MoCA 分数、不判断认知障碍 |

这意味着聊天模块和 MoCA 模块是互补关系：聊天更接近日常需要，MoCA 更接近标准化认知筛查；两者不能互相替代，也不能在本模块里混成一个诊断结论。

## 4. 目前已经实现的工作流程

1. 只取老人账号在当前聊天会话中说过的内容，最多 40 轮；不读取 AI 说的话来推断需求，也不读取家人私聊。
2. `deepseek-v4-flash` 生成固定 JSON，只允许两类信号：
   - `psychological`：陪伴、联系、孤独、参与活动等；
   - `physical_or_daily`：行动、睡眠、视听、日常自理、家务安全、身体不适等。
3. 每条信号必须附带内部 `source_turn_ids`，证明它来自当前会话；该编号只供服务端核验，不对家人展示。
4. 程序拒绝诊断、处方、用药调整、无效来源编号和复制聊天原话的输出。
5. 如果最新表达已说明“问题解决”“不用担心”“不需要帮助”，或内容不足、前后矛盾，系统输出“暂不形成关怀提示”。
6. 已绑定家人主动点击生成，页面只显示概括、类别和建议。

这个流程不依赖“把每句话嵌入隐空间”，也不要求长期保存完整聊天记录。

## 5. 为什么这些指标不是随便设置的

本模块的指标分为三类。它们的来源和含义不同，必须分开说。

### 5.1 成熟的通用指标：Precision、Recall、F1

把“是否识别到正确的关怀类别”看作多标签分类任务。Precision 衡量乱报，Recall 衡量漏报，F1 平衡两者；它们是信息检索与分类任务的标准度量，不是本项目发明。可参考 [Manning、Raghavan、Schütze 的《Introduction to Information Retrieval》](https://nlp.stanford.edu/IR-book/) 和 [Sokolova & Lapalme, 2009](https://doi.org/10.1016/j.ipm.2009.03.002)。

在当前 9 个最终 holdout 案例、每例 3 次的真实 API 运行中，按“案例—类别”计算：

| 已有实际结果 | 数值 | 表示什么 |
|---|---:|---|
| 类别 Precision | 90.9%（10 正确 / 11 输出） | 输出类别中有 1 次额外类别 |
| 类别 Recall | 83.3%（10 正确 / 12 应识别） | 2 次轻度、含蓄的线索被保守漏掉 |
| 类别 F1 | 87.0% | 两类错误的平衡值 |
| 无需推送时正确克制 | 15 / 15 | 普通闲聊、已解决、拒绝帮助时没有强推 |
| 合格结构化输出 | 27 / 27 | 每次都返回可校验、可展示的受限结构 |

这些是冻结合成案例上的真实运行结果，**不是**真实老人群体准确率或医学结论。

### 5.2 有论文方法支撑、按本项目改写的指标：行为鲁棒性

[CheckList（Ribeiro et al., ACL 2020）](https://aclanthology.org/2020.acl-main.442/) 的核心观点是：只看保留集准确率会掩盖 NLP 系统的行为错误，应该建立带预期结果的行为测试。

本项目据此设计四类成对案例：

| 本项目指标 | 论文方法对应 | 要验证的行为 |
|---|---|---|
| 已解决撤回率 | 状态变化的行为测试 | 后面明确解决后，旧提示应消失 |
| 拒绝尊重率 | 否定/意愿变化行为测试 | 老人明确不需要时，不应继续推送 |
| 改写一致率 | 同义改写不变性测试 | 换一种说法，核心判断不应改变 |
| 闲聊干扰稳定率 | 无关内容干扰测试 | 前后插入天气、兴趣聊天，不应破坏有效判断 |

这四项的名称是项目名称，不是论文中的固定术语；它们的**评测思想和“输入变化—预期行为”方式**来自 CheckList。最终需要在新增冻结案例上自动跑出数值，当前不虚构结果。

### 5.3 项目任务指标：行动匹配与保护规则

“家人行动匹配率”检查建议是否落到正确类型：陪伴联系、共同参与、日常分步协助、安全留意或暂不行动。它借鉴任务型对话里用“任务成功”衡量系统是否完成目标的思路；任务型系统研究也强调单个组件分数不一定代表整体任务表现，[Takanobu et al., SIGDIAL 2020](https://aclanthology.org/2020.sigdial-1.37/) 支持在早期用可控模拟评估替代昂贵真人评测。

“保护规则通过率”检查是否泄露原话、给出诊断、接受无效来源或越权展示。这不是学术指标名称，而是项目的安全合规验收条件；它必须是 100%，否则报告不应该展示。

### 5.4 证据支持率：只作补充，不冒充真值

可选的“证据支持率”把报告拆成原子主张，检查是否能被它标记的对话轮次支持。这借鉴 [FActScore](https://aclanthology.org/2023.emnlp-main.741/) 的原子事实核验与 [SummaC](https://aclanthology.org/2022.tacl-1.10/) 的细粒度对齐。

它适合发现“报告比聊天多说了什么”，但 NLI 或评委模型本身也会出错。因此它只能是内部拦截器和补充表格，**不能替代冻结案例的正确答案**。

## 6. 案例、数据集与“真实”的定义

### A. 本项目的受控参考案例：主评测数据

当前项目中已有：

- `care_report_frozen_cases.json`：16 个开发阶段冻结案例，用于改提示词和找问题；
- `care_report_final_holdout_cases.json`：9 个未参与提示词调整的最终案例，每例真实调用 3 次，共 27 次；
- 已保存只含案例编号、预期类别、实际类别和耗时的结果，不保存测试聊天原文或模型原文。

下一步的最终评测会把“预期行动类型”和成对改写/干扰字段补进冻结案例，形成 24 个主评测案例。正确答案会在运行前固定，代码不能根据结果回改答案。

这些案例是**受控参考案例**：它们能可靠地评测本项目定义的行为，但不能被包装为真实人群临床研究。

### B. 网上可查到的真实数据：只能做边界与场景支撑

| 数据 / 工作 | 真实程度与内容 | 在本项目中的正确用法 |
|---|---|---|
| [SeniorTalk](https://mlanthology.org/neurips/2025/chen2025neurips-seniortalk/) | 真实高龄人群自然中文语音对话；101 段对话、202 位参与者 | 支撑“老年自然语音场景存在且需要专门处理”；不能计算需求提取准确率 |
| [ESConv](https://github.com/thu-coai/Emotional-Support-Conversation) | 人工收集的情感支持对话；问题、情绪、支持策略与反馈标签 | 支撑“情感支持对话可以有可标注的问题与行动策略”；不能当老人家庭需求真值 |
| [COCOON](https://aclanthology.org/2025.emnlp-main.1094/) | 中文隐性情感需求与主动支持研究 | 支撑“从含蓄表达识别潜在需求”的技术方向；不能当老人身体/日常需求准确率数据 |

这部分写进报告的作用是说明项目不是凭空提出“隐性需求”，而是有相关对话研究和真实老人语言资源作支撑。它们的标签范围与项目不同，所以我们不跨范围宣称结果。

## 7. 这个模块怎样帮助老人实现实际需求

| 老人可能遇到的情形 | 模块能做到的第一步 | 由谁真正完成 |
|---|---|---|
| 不愿直接说孤单、想有人陪 | 给家人一个“可主动联系”的提示 | 家人打电话、视频、陪伴或安排活动 |
| 看不清表格、搬重物、处理生活事务吃力 | 提醒家人提供分步协助或帮忙处理 | 家人、社区或正式服务实际协助 |
| 出现影响出行或日常安全的不适描述 | 提醒家人主动询问、关注安全 | 家人根据实际情况陪伴、联系专业服务；系统不诊断 |
| 已解决或不想被打扰 | 不生成压力性提醒 | 老人的意愿得到尊重 |

所以，模块的价值不是“AI 替老人解决问题”，而是把原本可能被沉默掉的线索，变成一次由家人完成的真实行动机会。

## 8. 当前已证明、尚未证明的内容

| 已有证据 | 尚不能证明 |
|---|---|
| 聊天 → 受限结构 → 家人报告的链路可以真实运行 | 对所有真实老人都准确 |
| 27 次真实 API 调用均输出可校验结构 | 能发现所有潜在需求 |
| 未绑定家人被拦截，家庭页不显示原话 | 能诊断心理、认知或身体疾病 |
| 在当前最终案例中，普通闲聊、已解决与拒绝帮助没有被强推 | 一条报告一定能让家人采取行动或解决问题 |
| 现有 F1、稳定性和安全测试可复现 | 具有真实世界临床有效性 |

完成扩展冻结案例和五组自动化指标后，我们可以更有把握地说“系统在定义好的关怀情境中识别、克制、建议和抗干扰表现可复现”；仍然不能把它称作医疗验证。
