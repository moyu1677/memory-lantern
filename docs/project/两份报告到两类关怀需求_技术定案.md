# 两份报告到两类关怀需求：当前定案

## 先回答四个争议点

### 1. 老人每次说完话，要不要确认？

**不需要。** 日常陪伴若要求老人每说一句都看字、点确认，语音聊天就失去意义。

应采用“后台模型判断 + 只在不确定时自然追问”的方式：

```text
老人说话 → 语音识别（ASR）→ 模型得到识别置信度 → AI 回复
                                      ↓
                            低置信度才口头澄清一句
```

例如系统听不清时说：“我没有听清，您是说膝盖不舒服，还是腰不舒服？”而不是把一段文字丢给老人让他改。

只有三种会改变结果或泄露信息的操作，需要明确确认：正式评估的作答提交、一次性开通“可向已绑定家人发送关怀摘要”、以及修改分享对象。**不需要逐句确认，也不需要逐张需求卡确认。**

首次使用时，老人和家人只设置一次分享范围，例如：

> “您愿意让忆路明灯把它整理出的关心提示告诉小李吗？不会发送完整聊天记录。”

在此范围内，系统可以自动生成“关怀提示”。这正是 AI 的作用：老人不必把需求直接整理成一句正式请求，系统负责从自然聊天中整理线索；家人得到的是一个应当去关心和问一问的提示，而不是已被系统确认的事实或命令。

### 2. 两个核心模块怎样连成一个项目？

两个模块不是并排的两个功能，而是两份不同来源的证据，最终共同服务于同一个结果：**家庭关怀需求图**。

```text
标准化认知评估报告 ──→ 认知/生活支持线索 ─┐
                                             ├→ 家庭关怀需求图 → 家人简报
日常语音聊天报告 ────→ 情绪/身体自述线索 ─┘
```

最终只输出两类需求，而不是疾病分数：

| 需求维度 | 主要证据来源 | 家人得到的含义 |
| --- | --- | --- |
| 心理陪伴与社会连接需求 | 聊天中的孤独、情绪低落、想参与事情、回避麻烦家人等线索 | “最近值得多陪伴、主动聊一聊什么” |
| 生活与健康支持需求 | MoCA 所反映的认知支持线索 + 聊天中的身体不适、行动/睡眠/饮食/听力等自述 | “最近哪件生活或身体事值得具体询问、协助或考虑就医” |

这两个维度中的“生活与健康支持”不能写成“患了什么病”。MoCA 只能提供认知筛查信息；聊天只能提供老人自述和行为线索。系统最多提示“需要进一步关心/核实”，疾病判断仍属于医疗专业人员。

### 3. 谁是测试者，谁是被测试者？会不会自动弹题？

| 角色 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 老人（主要用户/被评估者） | 日常语音聊天；自主接受或拒绝一次评估邀请 | 看复杂文字、自己给自己下结论 |
| 施测者（接受 MoCA 规范培训的人员） | 在正式评估场景启动、按官方规则施测和计分 | 把正式 MoCA 改写成自由对话 |
| 家人（声音授权人与简报接收者） | 授权/撤回声音；接收已开通范围内的关怀提示；发起真实关心 | 查看完整私密聊天；替老人解释分数 |
| AI 系统 | 语音陪伴、朗读、记录、结构化整理报告 | 充当 MoCA 施测者、诊断疾病、假装家人本人 |

日常进入系统的默认页面应该是“开始聊一聊”，**不要自动弹出评估题**。正式 MoCA 必须在独立的评估场景中，由施测者发起；老人收到的只是一次可拒绝的语音邀请，例如“现在方便做一次认知小评估吗？大约十分钟，随时可以停下。”

若没有受过规范培训的施测者，就不能把结果称为正式 MoCA；此时只能叫“MoCA 领域参考的互动任务”。

### 4. 能不能用更好懂的话表达 MoCA？

这里必须二选一，不能同时满足：

| 路径 | 能否改变题目表达/内容 | 能否称为正式 MoCA |
| --- | --- | --- |
| 正式 MoCA | 不能。题干、材料、提示次数和计分必须按官方规则 | 可以，前提是满足官方使用和施测条件 |
| 老人友好改写版 | 可以按 MoCA 的认知维度把语言说得更容易懂 | 不可以，只能叫“MoCA 维度参考任务” |

这不是技术能力问题，而是量表标准化的基本要求：题目一旦改写，难度就可能变化，原有分数的意义也不再成立。

如果要保留正式 MoCA，又想让老人更容易操作，正确做法是把“**操作解释**”和“**正式题目**”分开：

1. 正式题目前，AI 用通俗话教会操作，例如“接下来请您在屏幕上画线，我们先试一下怎么用手指画”；
2. 正式题目开始后，严格使用官方规定的材料和提示；
3. AI 只做朗读与记录，不给额外暗示、解释或反馈。

MoCA 是用于认知筛查的专业工具，但也不是诊断本身；正式诊断仍需更完整的病史和医学评估。

## 一、统一后的产品定义

> **忆路明灯是一个以家人授权声音陪伴老人日常聊天、以标准化认知评估和自然对话两份报告为依据，向家人提供“心理陪伴”和“生活健康支持”关怀提示的系统。**

家人授权声音不是让 AI 冒充家人。每次对话开始都应清楚播报：

> “我是忆路明灯 AI，今天使用的是女儿授权的声音；这不是女儿本人正在通话。”

熟悉的声音降低老人开口的心理门槛；AI 的角色是陪伴、倾听和整理，不是替代家人。

## 二、两份报告如何形成一张关怀需求图

### 1. 认知评估报告：只提供“认知/生活支持线索”

若采用正式 MoCA，报告保留官方规定的领域与计分，由施测者解释。系统在给家人的关怀图中不显示“疾病标签”，只把结果转换为非诊断性的生活支持线索。

| MoCA 相关领域 | 可以生成的关怀线索 | 不可以生成的结论 |
| --- | --- | --- |
| 注意与记忆 | 复杂信息可分步骤说明；重要约定可用温和提醒 | “老人患有失智症” |
| 执行与视空间 | 涉及路线、表单、设备操作时可问是否需要陪同 | “老人无法独立生活” |
| 语言与定向 | 家人沟通时放慢节奏、一次只问一件事；如持续异常可建议专业评估 | “老人精神有问题” |

这些只是“沟通和支持方式建议”。MoCA 的单次结果不能直接推出老人孤独、患病或有某种具体生活需求。

### 2. 日常语音聊天报告：提取“自述事实 + 情绪/生活线索”

聊天分析的最小单位是**一次会话**，不是每一句话，也不需要为每句做向量或让老人确认。系统只保存/提取与关怀相关的有限字段：

```json
{
  "session_date": "2026-08-07",
  "psychological_signals": ["提到一个人在家无聊", "说不想打扰子女"],
  "physical_or_daily_signals": ["说上楼时膝盖疼"],
  "evidence": ["最近一个人在家，没什么意思", "膝盖一上楼就疼"],
  "explicit_request": null,
  "uncertainty": ["无法判断疼痛原因或严重程度"]
}
```

模型不能把“情绪低落”自动改写成“抑郁症”，也不能把“膝盖疼”自动改写成“关节炎”。

### 3. 关怀需求图：用证据强度，不用疾病概率

每个维度给出 `无明显线索 / 建议关心 / 建议尽快核实` 三档。这个档位来自可追溯证据，不使用不可解释的“模型内心分数”。

| 档位 | 形成条件 | 家人端措辞 |
| --- | --- | --- |
| 无明显线索 | 当前没有直接或重复相关表达 | “本周期未形成需特别关注的提示” |
| 建议关心 | 有一次明确表达，或多个较弱表达指向同一件事 | “他最近提到……，可以找机会问一问” |
| 建议尽快核实 | 同类问题跨会话重复出现；或老人明确表示影响日常生活；或正式评估显示需要由施测者进一步关注 | “建议近期和他确认这件事；如持续或加重，可考虑咨询专业人员” |

例子：

```text
聊天 1：最近一个人在家，没什么意思
聊天 2：你们忙，我自己待着就行
→ 心理陪伴与社会连接：建议关心
→ 给家人的话：最近两次聊天提到独处和不愿打扰家人。可以问：
  “这周末我陪您出去走走，还是您更想在家一起聊会儿？”

MoCA：注意/记忆相关项目需施测者关注
聊天：我总记不住下周的挂号时间
→ 生活与健康支持：建议尽快核实
→ 给家人的话：他提到记挂号时间有困难，且本次评估中需施测者进一步关注。
  可以先问他是否希望一起整理预约和提醒；不要直接说“您记忆退化了”。
```

## 三、现有量表怎么使用：用于“规范参照”和“模型验证”，不把问卷塞给老人

日常聊天本身不能替代临床量表。但现有量表可以在项目里承担两个非常有用的角色：

1. **定义系统应该关注什么**，避免 AI 随意发明“需求类别”；
2. **在小规模、知情同意的验证中作为对照标签**，检验聊天模型判断是否接近已有工具，而不是直接拿模型结论当真。

| 要判断的内容 | 可用的现有工具 | 在项目中的正确用法 |
| --- | --- | --- |
| 认知筛查 | MoCA | 正式施测模块；不能改题后仍称 MoCA |
| 孤独感/缺少陪伴 | UCLA Loneliness Scale；若需低负担可研究 3 项版 | 不要求每天填写；在模型验证时作为“孤独感”对照标签，或在老人愿意时偶尔做简短人工访谈 |
| 老年抑郁症状 | Geriatric Depression Scale（GDS，含 15 项短版） | 仅作为筛查参照，不把聊天情绪直接诊断为抑郁 |
| 日常基本自理能力 | Katz ADL | 用于判断洗漱、穿衣、如厕、进食等基本活动是否需要帮助，不用于诊断疾病 |
| 较复杂的独立生活能力 | Lawton IADL | 用于购物、出行、用药、处理事务等是否需要家人支持 |
| 身体、心理、认知等老年能力衰退线索 | WHO ICOPE 筛查框架 | 最适合作为“生活健康支持”类别字典；覆盖认知、心理、行动、营养、视觉和听力，但阳性结果仍需进一步评估 |

**推荐组合**：项目的正式评估用 MoCA；日常聊天报告的“心理陪伴”参照 UCLA-3/GDS-15 的关注范围；“生活健康支持”参照 WHO ICOPE 与 ADL/IADL 的关注范围。这样没有增加老人每天的问卷负担，却不会让模型凭空定义“健康”。

WHO 的 ICOPE 本身就把认知、心理、行动、营养、视觉和听力作为老年能力筛查领域；它很适合给第二类需求建立清晰边界，但它也不是疾病诊断。

参考来源：

- MoCA 原始验证研究：<https://pubmed.ncbi.nlm.nih.gov/15817019/>
- MoCA 官方使用条款：<https://mocacognition.com/terms-of-use>
- WHO ICOPE 人本评估指南：<https://www.who.int/publications/i/item/9789240103726>
- WHO ICOPE 筛查领域说明：<https://iris.who.int/bitstream/handle/10665/330026/WHO-FWC-ALC-19.2-eng.pdf>
- UCLA Loneliness Scale 验证研究：<https://pubmed.ncbi.nlm.nih.gov/8576833/>
- 中国老年人 UCLA-3 适配研究：<https://pubmed.ncbi.nlm.nih.gov/33303463/>
- GDS 原始验证研究：<https://pubmed.ncbi.nlm.nih.gov/7183759/>
- Katz ADL 综述：<https://pmc.ncbi.nlm.nih.gov/articles/PMC7320974/>

## 四、是否存在“提取老人需求”的现成模型？

没有一个可以直接拿来、就可靠判断“老人真正需要什么”或“老人有什么潜在疾病”的现成模型。原因很简单：真正需求要结合方言、家庭关系、老人表达习惯和后续确认；公开情绪数据集也通常不是老年人日常语音。

但可以使用现成模型搭建一个可验证的两层系统：

| 层级 | 可复用模型/技术 | 做什么 | 不做什么 |
| --- | --- | --- |
| 语音层 | 现有腾讯 ASR / 浏览器语音识别 | 把语音变成文字，并给出识别质量信息 | 用音色或停顿直接判断疾病/情绪 |
| 对话陪伴层 | 当前项目已接入的 DeepSeek；也可选 Qwen 指令模型 | 自然聊天、用家人授权声音回复 | 充当医生或正式 MoCA 施测者 |
| 信息抽取层 | 大语言模型按固定 JSON 输出；Qwen2.5 等指令模型擅长结构化 JSON 输出 | 从“最近几轮/本次会话”提取自述、情绪、身体/生活线索和原话依据 | 无依据地补全故事、给诊断名称 |
| 辅助分类层（可选） | 中文 MacBERT 等微调分类模型 | 将会话先分为“心理陪伴 / 生活健康 / 无关” | 替代人工定义标签，或输出医疗结论 |

对当前代码和七天范围，最合适的路径是：**保留现有 DeepSeek 聊天能力，在报告生成前增加一个严格 JSON 提取器和规则校验器；不要另起一套大模型训练。** 如果之后收集到足够、且取得同意并脱敏的标注会话，再用 MacBERT 做轻量分类器和对照实验。

MacBERT 是已公开的中文预训练模型，适合做中文文本分类；Qwen2.5 的模型说明也明确支持遵从指令和结构化 JSON 输出。它们解决的是“把话整理到规定字段”的问题，不会自动获得医疗判断能力。

参考：

- MacBERT 论文：<https://aclanthology.org/2020.findings-emnlp.58/>
- Qwen2.5 模型说明：<https://huggingface.co/Qwen/Qwen2.5-32B-Instruct/blob/main/README.md>

## 五、数据集与模型评测：真正要评什么

模型的“置信度”不是可靠性的证明，尤其不能直接把语音识别的置信度等同于健康判断。需要分别评估三件事。

### 1. 语音识别是否够用

建立一小组经同意的老人/模拟老人语音样本，覆盖普通话、常见方言、慢语速和环境噪声。人工写出正确文字，计算：

- 字错误率（WER/CER）；
- 低置信度时系统主动澄清的命中率；
- 澄清后意思被正确恢复的比例。

这解决的是“老人说的话有没有被听对”，不是“老人是否健康”。

### 2. 需求信号有没有被正确抽取

标注单位是“一段完整会话”，而不是单句。每段由至少两位标注者独立标注：

```text
心理陪伴线索：无 / 孤独或社交缺失 / 情绪低落 / 希望参与活动 / 不愿麻烦家人
生活健康线索：无 / 身体不适 / 行动受限 / 睡眠饮食 / 听力视觉 / 日常事务困难
证据原话：必须圈出对话中的支持句
强度：无明显线索 / 建议关心 / 建议尽快核实
```

模型与人工标注比较 `Precision（少误报）`、`Recall（少漏报）` 和 `Macro-F1`。面向家人的普通提示应优先提高 Precision，避免频繁“误报”让家人失去信任；涉及预先定义的紧急风险词时，宁可由安全流程优先处理并交给人工核实。

### 3. 两份报告融合后是否真的有价值

在得到同意的小样本中，不要求老人每天答问卷，只在验证时由人工完成一次 UCLA-3、GDS-15、ADL/IADL 或 ICOPE 相关评估，再比较：

- 模型提示“心理陪伴需要关注”的会话，是否更常对应孤独/情绪筛查的阳性或较高分组；
- 模型提示“生活健康支持需要关注”的会话，是否更常对应 ADL/IADL 或 ICOPE 中需要进一步了解的领域；
- 家人是否能在一分钟内理解简报，并写出合适的关心开场句。

这才是“模型评测指标”的正确位置：评估**模型提取的准确性和报告的可用性**，而不是让模型给老人一个病情分数。

## 六、与现有代码的关系

现有项目已经有语音输入、普通聊天、十题互动、结果报告、家人绑定和 DeepSeek/RAG 底座。要实现当前定案，代码层面只需要围绕同一份“关怀需求图”补四件事：

1. 将聊天会话按有限窗口送入 JSON 提取器，保存“类别、证据原话、不确定项”，而不是保存一个不可解释的情感分数；
2. 让 MoCA/任务报告输出结构化领域结果，再由固定规则产生“生活支持线索”；正式 MoCA 与现有十题不能混用；
3. 新增一次性的分享权限和家人可见范围；家人只见关怀摘要和证据片段，不见完整聊天；
4. 把两类线索汇总成一页家人简报：心理陪伴、生活健康支持、依据、建议怎样开口。

当前不应做的事：逐句确认、自动弹出考试、每句话进向量库、让模型诊断疾病、把聊天和 MoCA 合成一个医疗风险总分。
