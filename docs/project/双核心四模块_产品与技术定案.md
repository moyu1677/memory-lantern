# 忆路明灯：双核心、四模块产品与技术定案

## 0. 这到底是一个什么东西

它不是“用 AI 给老人下健康结论”的产品，也不是把老人每天的聊天记录全部交给家人看的监控工具。

它是一个面向老人的**语音优先陪伴入口**，同时给家人一个**经过老人确认、能快速理解的沟通线索**。陪伴对话可使用经授权的家人声音，使老人听到更有熟悉感的声音；但系统必须持续说明它是 AI，不是假扮家人本人。系统做两件不同的事：

1. 用低负担的小任务，记录老人当次完成认知相关任务时的表现和作答条件；
2. 在老人主动提到具体生活困难、偏好或愿望时，帮助他说清楚，并在他同意后把这件事整理成一张给家人的“需求卡”。

系统不能诊断认知障碍，也不能从一句普通聊天中猜出老人没说出口的需求。它的价值是：把原本容易被忽略、又不便直接开口的事情，变成老人可控、家人可行动的沟通起点。

## 1. 先把 MoCA 的边界说清楚

MoCA 是 **Montreal Cognitive Assessment（蒙特利尔认知评估）**，源自加拿大，并不是“美国的量表”。它是一套标准化的认知筛查工具，涉及视空间/执行、命名、注意、语言、抽象、延迟回忆、定向等多个方面。

这里有一个不能混淆的事实：

- 正式 MoCA 是经过验证、用于辅助识别轻度认知障碍的专业筛查工具；其价值来自统一的题目、施测方式和评分规则。
- 直接使用正式 MoCA 题目、评分和名称，属于正式量表的使用；官方对临床、研究和教学中的施测、计分与解释设有培训/认证与使用条件。
- MoCA 不全是口头题，包含视空间/执行类的画线、立方体、画钟等内容。因此“全语音、AI 自动改写题目”的版本不能再说是正式 MoCA。
- 把正式题目删减、改成对话或自行改写评分后，不能再说它是“MoCA 测评”，更不能把总分解释成诊断结果。
- 现有项目的“10 题、14 分”题库不是完整 MoCA，不能包装成 MoCA，也不应给出“患病/未患病”结论。

如果团队能取得官方相应语言版本、按官方规则施测，并由完成官方培训/认证的人员负责施测与计分，那么第一板块可以直接叫：

> **“标准化 MoCA 认知筛查记录”**

此时系统的作用是把标准化流程做得更容易操作：语音朗读题干、清晰呈现图形题、记录答案、保存正式施测者给出的结果；它不能自行改题、替代施测者解释结果。

如果不能满足这些条件，项目中合适的表述才是：

> **“参考 MoCA 所覆盖的认知领域设计的低负担互动任务”**

它的输出名称是“任务表现记录”或“认知互动观察”，不是“MoCA 总分”“认知障碍诊断”。如果项目必须展示真正的 MoCA，应由有相应资格和授权的人在系统外完成施测；本系统最多记录经本人同意录入的结果，不能替代它。

这并不是弱化项目，反而让项目的边界可信。WHO 也明确指出，正式的痴呆诊断还需要更详细的病史、医学评估和精神状态检查，单个简短认知测试只能作为辅助信息。

## 2. 两个核心板块，不合并成一个分数

| 板块 | 老人看到的东西 | 系统得到的东西 | 家人看到的东西 | 系统绝不能做的事 |
| --- | --- | --- | --- | --- |
| A. 轻量任务与作答质量 | 简短、可跳过的语音/点击互动 | 每题表现 + 本次作答条件 | 如老人同意，可见“本次任务记录”和注意事项 | 用一次结果判断认知障碍、生成疾病结论 |
| B. 需求沟通桥梁 | 自然聊天；必要时一句温和追问 | 经本人确认的生活需求卡 | 最多几张有依据、可对话的需求卡 | 监视老人和家人的私聊；猜测未表达的需求；强制分享 |

这两个板块必须分开呈现。任务表现回答的是“这次任务完成得怎样、这次结果是否可靠”；聊天回答的是“老人愿意让家人知道什么”。

把两者合成一个“健康/风险总分”会造成两个问题：既不科学，也容易让家人误以为系统已经下了结论。

## 3. 四个模块如何收束

### 模块一：语音聊天、可信陪伴与防诈骗提醒

**真正要做的功能**：老人按住/点击“说话”后，直接用语音和 AI 聊天；系统同时完成语音识别、理解和语音回复。老人不需要像打字聊天那样逐字看屏幕、逐句修改。AI 以陪伴和生活对话为主，不把每句话都自动分析给家人。

自然聊天和正式操作应区分处理：普通聊天在语音识别置信度足够高时可以直接发送，让对话保持自然；识别不确定时，AI 用语音确认“我听到的是……对吗？”。涉及**MoCA 作答提交、生成需求卡、分享给家人、任何转账/验证码提示**时，必须由老人再确认一次，不能靠系统猜测。

**需求引导只在合适的时候发生**：

1. 老人自然说出一个具体生活事实，例如“这两天买菜不太方便”；
2. AI 最多追问一句，例如“这件事让您觉得最麻烦的是什么？”；
3. 老人自己说出困难、希望或偏好；
4. AI 用一句话复述，请他确认：“我理解为您希望家人知道……，可以吗？”；
5. 只有明确同意，才生成可分享的需求卡。

老人拒绝、改话题或没有确认，系统立刻停止追问，也不分享。这是整个产品最重要的信任规则。

**家人授权声音可以成为第一版的核心体验。** 你的判断是成立的：对一个本来不愿意面对冰冷机器音的老人来说，熟悉的人声能降低开口门槛，让陪伴功能更像一次自然交谈。它的定位应是“由 AI 进行陪伴对话、使用家人授权的声音表达”，而不是“让 AI 假装成家人”。

每次进入对话时，系统应明确说和显示：**“我是忆路明灯 AI，今天使用的是女儿小李授权的声音；这不是小李本人正在通话。”** 这样既保留熟悉感，也不欺骗老人。

声音功能必须有四条硬规则：

1. 声音所有者单独授权，指定可使用的范围；
2. 老人可选择是否听这个声音，也可以切换为普通温和声音；
3. 合成声音只在应用内实时播放，不提供下载、转发或用于电话外呼；
4. 声音所有者可随时撤回授权并删除声音资料；每个生成语音界面都标明“合成语音”。

这样，防诈骗功能不是和声音克隆对立，而是让老人知道“应用内、明确标识的 AI 家人声音”和“电话里任何自称家人的声音”不是一回事。涉及转账、验证码、陌生来电等话题时，系统只做“二次核验提醒”：先挂断，再通过熟悉号码联系家人确认；不能声称能自动识别所有诈骗。

### 模块二：老人友好界面

这不是给普通网页放大字体，而是让老人能知道“现在在做什么、下一步怎么做、出错后怎么办”。界面只保留三条主入口：**聊一聊、做个小互动、听家人留言**。

每一页遵守以下规则：

- 一屏只让老人完成一件事；按钮用文字加图标，避免只用抽象图标；
- 大字、强对比、清楚的朗读/返回/退出；
- 普通聊天允许高置信度语音直接进入对话；识别不清时由 AI 语音复述确认。评分、分享等关键操作必须明确确认；
- 任务可暂停、跳过和结束，没有倒计时羞辱或“答错”提示；
- 分享前再次说明“这张卡会给谁看、内容是什么”。

### 模块三：低负担任务，不把压力转嫁给老人

如果采用正式 MoCA，这里不应该增加自创认知题目或自创认知维度。正式量表本身已经覆盖了它设计要覆盖的内容；多加题只会破坏标准化。真正需要记录的不是新的“评测指标”，而是**本次施测是否出现技术或使用条件问题**。

无论是正式 MoCA 还是现有原型互动，都至少保留两层记录：

| 第一层：任务表现 | 第二层：作答条件（结果可靠性） |
| --- | --- |
| 每道互动的完成/未完成、需要提示次数、是否跳过 | 输入方式（语音/点选）、语音转写是否经本人确认、停顿/重复次数、是否中断、是否主动说“听不清/累了/不想做” |

第二层不是额外的认知分数，也不能影响 MoCA 标准得分；它只用于避免技术误判。例如老人答得慢，可能是听力、网络、方言识别、疲劳或不会操作，而不等于认知变差。报告应写“本次存在语音识别反复确认，建议由施测者判断是否重新进行”，而不是把原因归到老人身上。

若走正式 MoCA 路径，现有十题不能和 MoCA 混用，应从评估模块移出，最多保留为不计分的益智互动。若暂时只能走原型路径，现有十题可以保留为“认知互动任务”，但应做三项修正：

1. 题目和任务域逐题标注来源与意图，删除无法解释或只靠关键词判分的题；
2. 语音答案必须由老人确认文字后才评分；
3. 报告从“百分比和等级结论”改成“完成情况 + 作答条件 + 必要时建议与专业人员沟通”。

### 模块四：双来源报告，让家人一分钟看懂

报告不是长篇分析，也不是把聊天记录转发给家人。它由两个彼此独立的区域组成。

**区域 A：本次互动记录（来自小任务）**

- 完成了哪些类型的任务；
- 本次出现了哪些会影响结果的条件，例如“语音多次未识别”“中途主动暂停”；
- 只使用中性语言：例如“可在状态较放松时再尝试”，不写“认知下降”。

**区域 B：老人确认分享的生活需求（来自聊天）**

每张需求卡固定四项：

| 字段 | 说明 |
| --- | --- |
| 老人想让家人知道什么 | 用老人确认过的一句话概括 |
| 对话依据 | 只保留支撑这张卡的一小段原话或经确认的转述 |
| 老人希望的帮助/偏好 | 例如“希望有人教一次线上挂号”，也允许写“暂时不需要帮助，只希望被听见” |
| 家人可以怎样开口 | 给一句非命令式开场，例如“您上次提到挂号不方便，想不想和我说说是哪一步卡住了？” |

家人首页最多展示三张待关注卡，按“老人希望优先处理”“仍未回应”“最近确认”排序。报告的目标是让家人少猜一点、能更自然地开始一次真实交流，不是替家人做决定。

## 4. 这条技术路径怎样落地

不需要把每一句话塞进“隐空间”，也不需要先上向量数据库。

因为本项目要交付的不是“把所有聊天做相似度检索”，而是少量、可追溯、经同意的需求卡。先把规则做对，比堆复杂模型重要。

### 4.1 聊天到需求卡：一个受约束的状态机

```text
普通聊天
  → 出现具体生活事实
  → 一次温和追问（可跳过）
  → 老人表达影响/偏好
  → AI 复述
  → 老人明确同意分享
  → 写入需求卡并生成家人简报
```

代码中可以拆成五个小函数，而不是一个难以控制的大提示词：

```text
detect_concrete_life_fact()      # 判断是否值得温和追问
choose_one_follow_up()           # 只生成一个短追问
extract_candidate_need()         # 提取“事情、影响、偏好”，不直接分享
confirm_and_create_card()        # 必须等老人明确同意
build_family_brief()             # 从已同意的卡片生成极短简报
```

大模型只负责从本轮有限上下文中按固定 JSON 字段整理候选信息；程序负责控制次数、确认、权限和保存。候选 JSON 至少有：`事实`、`老人原话`、`影响`、`希望/偏好`、`是否已确认`、`是否同意分享`、`不确定点`。任一关键字段缺失，就不生成家人卡片。

这样可解释性来自“每张卡都能回到老人确认过的依据”，而不是来自一个无法向用户解释的向量距离。

### 4.2 任务记录：把“分数”与“条件”分离

现有 `assessments` 数据中只有作答和分数。应增加独立的 `task_context` 记录：

```text
assessment_id
input_mode                 # voice / touch
transcript_confirmed       # 语音转写是否由本人确认
retry_count                # 重说/重试次数
pause_or_abandon           # 暂停、跳过、中断
self_reported_barrier      # 听不清、疲劳、不会操作等（可为空）
```

系统生成的只是“结果可靠性提示”，例如：

```text
若未确认转写，或中断/重试达到预设阈值：
  标记为“本次受使用条件影响，交由施测者判断是否重测”
否则：
  标记为“本次记录可供施测者按标准规则计分”
```

阈值要写死在配置和报告说明里，不能让模型随意决定。模型也不应该从停顿直接推断认知问题。

### 4.3 最小数据结构与权限

```text
conversation_sessions     # 会话本身；可设置保存期限
need_cards                # 仅保存候选/已确认的需求卡和证据片段
share_consents            # 卡片、分享对象、同意时间、撤回状态
family_briefs             # 家人实际看到的短简报
task_context              # 任务条件，不和健康结论混在一起
voice_profiles            # 授权人、使用范围、撤回状态、语音服务商的受控引用
```

家人只能看到：该老人已经同意、且未撤回、且分享对象匹配的卡片。不能因为“已绑定家人”就读取完整聊天、全部历史或所有测评结果。撤回后，家人端立即隐藏卡片；原始对话按预先说明的期限删除或不保存。

## 5. 现有代码和目标之间，实际差在哪里

当前项目已经有 Flask 页面、语音输入、普通聊天、十题互动、结果报告、家人绑定和知识库，这些足以作为演示原型的底座。

但它现在还没有以下关键能力：

| 目标能力 | 当前状态 | 必须补上的最小变化 |
| --- | --- | --- |
| 自然语音对话与关键操作确认 | 当前语音转写会自动发送 | 普通聊天按识别置信度处理；评分、分享等关键操作必须二次确认 |
| 家人授权声音陪伴 | 当前没有受控的家人声音能力 | 增加 `voice_profiles`、双向知情提示、应用内播放、撤回/删除机制 |
| 对话变成可解释需求卡 | 当前聊天只是陪伴/RAG 问答 | 增加受约束的需求引导状态和 `need_cards` |
| 老人逐张同意分享 | 当前绑定家人可直接读取较多历史内容 | 增加卡片级同意、撤回与分享对象校验 |
| 双来源报告 | 当前报告主要来自一次题目得分 | 分为任务记录与已确认需求卡，绝不合成健康分数 |
| 结果可靠性 | 当前只有答案和分数 | 保存语音确认、重试、中断和自述障碍 |
| 真正的反诈保障 | 当前只能作为提示语 | 明确为“二次核验提醒”；不承诺自动识别诈骗 |

## 6. 这个项目是否“足够”——用可验证条件回答

只要下面的条件能被演示和测试，这个项目就已经是一个完整而聚焦的课程项目；不需要再扩展成医疗平台、全天候监测平台或复杂心理画像系统。

1. 老人能完成一次语音聊天；高置信度转写可保持自然对话，识别不确定时会由 AI 语音确认；
2. 老人说出具体困难后，AI 只追问一次，并能让他确认或拒绝分享；
3. 家人只能看到一张有老人确认依据的需求卡，不能看到整段私密聊天；
4. 标准化评估记录能清楚区分“按量表规则给出的结果”和“本次是否受语音/疲劳/操作影响”；
5. 页面始终说明：这不是诊断，异常或持续担忧应由家人和专业人员进一步沟通；
6. “家人授权声音”能演示授权、AI 身份提示、应用内使用、标识和撤回；
7. 所有需求卡都可追溯到已确认原话；没有依据就不展示给家人。

这七项比“更多题目、更多指标、一个更高的 AI 分数”更能证明产品真的解决了老人和家人之间的沟通问题。
