# 忆路明灯：代际需求翻译引擎技术路线（收敛版）

## 先定一个关键技术决定

**不把每一句话、每段原始聊天都存进“隐空间”，也不建设向量数据库作为项目主线。**

技术上，这当然可行；向量库也不会真的把所有句子两两组合比较。但它不适合本项目：数据少、方言转写会有误差、否定词可能改变整句意思，而且很难向老师和家人解释“为什么这两句话被认为相似”。

例如：

```text
“我想让你回来看看。”
“我不想让你特地回来。”
```

只差一个“不”，真实意图可能完全相反。不能让向量距离替代这种判断。

因此，项目的技术核心不是“隐空间判定需求”，而是：

> **模型把一次自然聊天翻译成可核查的“需求卡”；团队设计的明确规则再把多张需求卡整理成家属简报。**

这更简单、更可靠，也仍然有技术含量。

---

## 1. 系统做什么

```text
老人自然聊天
    ↓
模型只在一次完整聊天结束后，生成一张结构化需求卡
    ↓
规则检查：是否直接表达、是否有原话、是否在不同聊天重复出现
    ↓
只把证据充分的内容放进家属简报
    ↓
家人自己理解、联系和行动
```

老人不用填问卷；家人不需要天天查看；模型不判断疾病。

### 一个不能越过的边界

系统**只能理解老人实际对 AI 说过的话**，不能读取老人和家人的私聊，更不能把家人语境中的客套话臆测为老人对 AI 的需求。

因此，单纯“被动抽取聊天内容”不够。AI 必须具备一种低压力的**需求引导对话能力**：老人先自然提到生活中的某件事，AI 再顺着这件事了解它是否造成不便、老人希望怎样处理、以及是否愿意让家人知道。老人没有提到、拒绝继续谈、或不同意分享时，系统就停止，不猜测、不上报。

---

## 2. 会话级需求卡：模型实际承担什么

系统不是逐句嵌入，而是把一轮自然聊天（例如 1–3 分钟）作为一个单位。

### 需求引导会话状态机

AI 不会每天抛出“你有什么困难吗”之类的问题，也不会像问卷一样连续追问。它只在老人已经主动提到一个具体生活事实后，顺着语境最多问一个温和问题：

```text
状态 0：尚无生活线索
    → 正常聊天，不探询需求。

状态 1：老人自然提到具体事实
    → 例如：“阳台灯还没修。”
    → AI 可问一次：“晚上用阳台会不会不太方便？”

状态 2：老人表达实际影响或个人想法
    → 例如：“晾衣服时看不清。”
    → AI 可问一次：“您更想自己处理，还是让我帮您记着，之后由您决定要不要告诉家人？”

状态 3：老人明确选择分享
    → 生成可供家属查看的需求卡。

结束状态：老人拒绝、换话题、语音不确定
    → 不生成家属卡；同一话题在一段冷却期内不再追问。
```

这不是“读心”，而是给不擅长直接开口的老人一个自然、安全的表达机会。

语音转文字后，模型返回受限制的 JSON，而不是自由写总结：

```json
{
  "session_id": "S20260806_03",
  "confirmed": true,
  "items": [
    {
      "category": "居家事务",
      "subject": "阳台照明",
      "polarity": "needs_help",
      "directness": "indirect",
      "evidence": "阳台灯又坏了，晚上黑乎乎的",
      "confidence": "medium"
    },
    {
      "category": "家庭联系",
      "subject": "孙子",
      "polarity": "mentions_interest",
      "directness": "indirect",
      "evidence": "上次小孙子说要回来，不知道什么时候有空",
      "confidence": "medium"
    }
  ]
}
```

### 固定类别，而不是无限标签

只允许下面八类，避免模型无限发挥：

1. 居家事务；
2. 出行与生活安排；
3. 身体不适的原话；
4. 家庭联系；
5. 社交与情感表达；
6. 兴趣和愿望；
7. 需要的服务或物品；
8. 互动偏好（疲劳、听不清、想慢一点）。

`polarity` 也必须固定为：`needs_help`、`declines_help`、`mentions_interest`、`uncertain`。这一步专门防止“想”和“不想”被混为一谈。

模型只做两件事：理解自然语言，填入限定字段。它不能输出“老人孤独”“认知下降”“需要就医”等健康判断。

---

## 3. 真正的核心：证据规则，而非距离规则

每张需求卡进入一个很小、可解释的“需求台账”。是否展示给家人由固定规则决定：

```text
规则 A：老人明确提出帮助请求，或明确表示“可以让家人知道”，且语音文本已确认
        → 可以进入本周简报，标记为“老人提到”。

规则 B：不是直接请求，但同一类别、同一主题在至少两次不同聊天中出现
        → 可以进入简报，标记为“值得留意”。

规则 C：只有一次间接表达，或模型置信度低，或语音未确认
        → 不展示给家人；只留在下一次聊天的私密上下文。

规则 D：表达为“拒绝帮助”“不想继续谈”或“不愿分享”
        → 绝不改写成“需要帮助”；不生成家属卡；进入冷却期。
```

因此系统的逻辑不是“两个向量距离近，所以它有需求”，而是：

> **这件事说了什么、态度是什么、是否重复出现、证据是否够。**

---

## 4. 家属得到的不是提示，而是可行动的理解

每周最多三张卡，每张卡都有固定结构：

```text
本周线索：阳台照明问题在两次聊天中出现。
表达方式：老人没有直接请求帮忙。
可从哪里开始聊：可以自然问问“阳台灯后来修好了吗？”
依据：最近一次为今天；另一次为 3 天前。
```

这不是要求家人照着系统执行，也不是一句空泛提醒。它把老人不愿直接说的生活信息和关系线索压缩出来，让家人自行决定怎样联系、是否上门、是否帮忙。

家人默认看不到完整对话、完整转写和原始录音；只有在老人授权后，才看这类摘要卡。

---

## 5. “隐空间”还要不要

### 本轮最小版本：不要

不需要主动构建、保存或查询老人聊天的隐空间。大模型在理解一句话时本身会使用内部表示，但那是模型内部能力；项目不需要把它变成一个难以控制的用户画像库。

### 以后有真实需求时：只作辅助，不作裁决

若后续发现固定类别无法把“买不动菜”“下楼太费劲”归为同一话题，可以只给**已经人工/规则确认的需求卡标题**做小规模向量化：

```text
最多保存最近 20–30 张已确认需求卡的摘要向量
        ↓
只用于给模型找可能相关的旧卡
        ↓
仍由规则 A–D 决定是否进入家属简报
```

原始对话不嵌入；向量相似度不作最终决定；包含否定词、数字、时间、人名的句子必须回看原话。

这样既保留了语义模型未来的扩展性，又不让它破坏可解释性。

## 6. 代码结构：只新增一个小引擎

新增 `needs_engine.py` 即可，职责保持明确：

```text
extract_session_card(transcript)
    已确认的一轮聊天 → 固定 JSON 需求卡

validate_card(card, transcript)
    检查类别、态度、原话是否存在；失败则丢弃

update_need_ledger(elder_id, card)
    更新“同一主题出现过几次、最后一次何时出现”

build_family_brief(elder_id, policy)
    按规则 A–D 生成最多三张家属卡
```

SQLite 只需新增四张表：

```text
conversation_sessions  一轮聊天的确认状态与时间
need_cards             模型输出的受限 JSON 与原话证据
need_ledger            分类、主题、出现次数、最后出现时间、态度
family_briefs          已生成卡片和当时的授权快照
```

现有 `app.py` 负责在聊天完成后调用引擎；`database.py` 存取台账；现有绑定关系只保留为“谁能查看”，还需新增老人授权开关。当前 RAG 知识库不参与个人需求判断。

## 7. 可以真实跑出的技术指标

| 指标 | 怎么测 | 说明 |
| --- | --- | --- |
| 需求卡字段准确率 | 人工标注对话与模型 JSON 比较 | 模型有没有提取对类别、主题、态度 |
| 否定识别错误率 | 专门构造“想/不想、需要/不需要”等对照句 | 防止一句话反义被误判 |
| 原话证据覆盖率 | 有 evidence 的家属卡数 / 全部家属卡数 | 目标为 100% |
| 无依据生成率 | 找不到原话支撑的结论数 / 全部结论数 | 目标为 0 |
| 跨会话聚合准确率 | 重复/不重复情境的规则输出是否符合预期 | 验证规则 A–D |
| 家属阅读负担 | 每周卡片数、总字数、预计阅读时间 | 最多 3 张，约 1 分钟 |
| 授权拦截率 | 未授权访问被阻止的比例 | 目标为 100% |

这验证的是“系统能否把自然聊天可靠地翻译给家人”，不验证老人是否健康。

## 8. 最小演示

只需两段虚拟对话：

```text
老人：“阳台灯还没修。”
AI：“晚上用阳台会不会不太方便？”
老人：“晾衣服时看不清。下次儿子来让他顺便看看吧。”
AI：“我可以只把‘阳台照明不方便、希望下次顺便看看’记进家属摘要，
      不放完整聊天。可以吗？”
老人：“可以。”
```

展示顺序：

```text
老人自然提到生活事实
    ↓
AI 的一次上下文追问
    ↓
老人说出影响、偏好和分享许可
    ↓
获得授权的家属看到一张带证据的关怀卡
```

这足以说明模型不是简单关键词匹配，也没有把向量相似度当作黑箱裁决。
